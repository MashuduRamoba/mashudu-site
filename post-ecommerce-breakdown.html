How I Built a Full E-Commerce Site with React.js From Scratch

A deep dive into my TUT academic project — 14 products, live cart, 3-step checkout, React Context state management, and full mobile responsiveness. Every decision explained.

MR
Mashudu Ramoba
Software Developer · React.js · TUT Graduate

For my TUT Web Development module, I was tasked with building a fully functional e-commerce website. I could have built something basic — a few static HTML pages with some CSS styling. Instead, I decided to build something I'd actually be proud to show in job interviews: a production-quality React.js application with real features, real state management, and real responsive design.

This post breaks down every major decision I made — what I built, why I built it that way, and what I learned in the process.

The Requirements

The brief was straightforward: build a responsive e-commerce website. That was essentially it. The freedom was intentional — the module wanted us to demonstrate initiative and real-world thinking, not just follow a template.

I set my own requirements:

  • At least 10 products across multiple categories
  • Working shopping cart with quantity management
  • Product search and category filtering
  • Full checkout flow with form validation
  • Fully mobile responsive
  • No backend — pure frontend (scope limitation)

Architecture Decision: Why React?

I could have built this in plain HTML, CSS, and JavaScript. For a small static site, that would have been fine. But I chose React for three reasons:

  • Component reusability — a ProductCard component written once, used everywhere
  • State management — the cart needed to be accessible from multiple pages simultaneously
  • Real-world relevance — React is the most in-demand frontend framework for junior roles

The Hardest Part: Cart State Management

The shopping cart was the most technically challenging part of the project. The cart needed to be accessible from the Navbar (to show item count), the CartDrawer, the ProductCard (to show "In Cart" state), and the Checkout page — all simultaneously.

I used React Context API with useReducer — the same pattern used in production apps before Redux becomes necessary.

{`// CartContext.js — the core reducer
function cartReducer(state, action) {
  switch (action.type) {
    case "ADD": {
      const exists = state.items.find(
        i => i.product.id === action.product.id
      );
      if (exists) {
        // Increase quantity if already in cart
        return {
          ...state,
          items: state.items.map(i =>
            i.product.id === action.product.id
              ? { ...i, quantity: i.quantity + action.qty }
              : i
          ),
        };
      }
      // Add new item
      return {
        ...state,
        items: [...state.items, {
          product: action.product,
          quantity: action.qty
        }]
      };
    }
    case "REMOVE":
      return {
        ...state,
        items: state.items.filter(
          i => i.product.id !== action.id
        )
      };
    case "UPDATE_QTY":
      if (action.qty <= 0)
        return {
          ...state,
          items: state.items.filter(
            i => i.product.id !== action.id
          )
        };
      return {
        ...state,
        items: state.items.map(i =>
          i.product.id === action.id
            ? { ...i, quantity: action.qty }
            : i
        )
      };
    case "CLEAR":
      return { ...state, items: [] };
    default:
      return state;
  }
}`}
💡 Why useReducer instead of useState?

When state logic involves multiple sub-values or the next state depends on the previous one (like a cart), useReducer is cleaner and easier to test than useState. Each action type is explicit and predictable.

Search, Filter & Sort — useMemo for Performance

The Shop page needed to filter 14 products by category, search by name/description, and sort by price/rating simultaneously. Running this computation on every keystroke without optimisation would cause unnecessary re-renders.

I used useMemo to cache the filtered result and only recompute when the relevant dependencies change:

{`const filtered = useMemo(() => {
  let list = activeCat === "all"
    ? PRODUCTS
    : PRODUCTS.filter(p => p.category === activeCat);

  if (search) {
    const q = search.toLowerCase();
    list = list.filter(p =>
      p.name.toLowerCase().includes(q) ||
      p.description.toLowerCase().includes(q)
    );
  }

  switch (sort) {
    case "price-asc":  return [...list].sort((a,b) => a.price - b.price);
    case "price-desc": return [...list].sort((a,b) => b.price - a.price);
    case "rating":     return [...list].sort((a,b) => b.rating - a.rating);
    default:           return list;
  }
}, [activeCat, search, sort]);`}

3-Step Checkout with Form Validation

The checkout flow has three steps: Personal Details → Shipping Address → Payment. Each step validates its own fields before allowing progression to the next.

I built a reusable validation function that checks required fields and returns an errors object, then displays inline error messages under each field. This is the same pattern used in production forms — not just turning inputs red, but giving users clear, specific feedback.

Mobile Responsiveness

I used CSS Grid with auto-fill and minmax for the product grid — it automatically adjusts from 4 columns on desktop to 2 on tablet to 1 on mobile without any media queries on the grid itself:

{`display: grid;
grid-template-columns: repeat(auto-fill, minmax(260px, 1fr));
gap: 1.5rem;`}
✅ Best Practice

Use auto-fill with minmax for product grids. It's more flexible than hardcoded breakpoints and handles edge cases (like very wide screens or narrow tablets) automatically.

What I Would Do Differently

  • Add a real backend — Node.js + Express API with a database instead of static product data
  • Add user authentication — login, saved addresses, order history
  • Add real payment integration — Stripe or PayFast for South African payments
  • Write tests — Jest + React Testing Library for the cart logic at minimum

KEY TAKEAWAYS

  • React Context + useReducer is the right pattern for shared state like a cart
  • useMemo prevents unnecessary recomputation on filtered/sorted lists
  • CSS Grid with auto-fill/minmax handles responsive layouts elegantly
  • Form validation should give specific feedback, not just highlight errors
  • Build projects you're proud to show — then write about what you built
